## 1. 目标与约束（MUST）

本节目标对应 PRD 验收标准（见 `PRD-实时交互数字人助手.md` §3，引用不复制）：

- 端到端延迟 < 2s、TTFT < 1s、音画时差 < 50ms、打断响应 < 200ms、单卡并发 N 路
- 固定测试集 20-30 条 + 同口径回归台账；README 含架构图/延迟瀑布图/指标表/demo 脚本

约束条件：

| 约束 | 说明 |
|---|---|
| 模型全部开源，不训练 | 口型/语音识别/语音合成均用开源模型（选型见 ADR-003 及本文件 §5） |
| 编排全链路自研 | 不引入开源整包，链路每一行可解释（ADR-002） |
| 推理实验在云 GPU | 本机做链路开发与调试，口型推理/压测在云 GPU（ADR-001） |
| 浏览器播放 | WebRTC 输出，不做移动端/小程序 |
| 形象通用 | 通用虚拟形象，不做真人克隆 |

## 3. 系统流程（HUMAN）

### 3.1 总体架构（状态机：听 → 想 → 说 → 演）

```
┌─────────────────────────────────────────────────────────┐
│                 React 前端（浏览器）                      │
│            语音采集 / 视频播放 / 打断按钮                  │
└──────────────────────┬──────────────────────────────────┘
                       │ WebRTC / SSE
┌──────────────────────▼──────────────────────────────────┐
│              FastAPI 网关 + 会话状态机                    │
│    听(ASR) → 想(LLM) → 说(TTS) → 演(口型+渲染)          │
│    每段打点计时（延迟瀑布图数据源）                        │
└───┬──────────┬──────────┬──────────┬───────────────────┘
    │          │          │          │
┌───▼───┐ ┌───▼────┐ ┌───▼────┐ ┌──▼──────────┐
│ FunASR │ │ DeepSeek│ │ CosyVoice│ │ MuseTalk +   │
│ 流式ASR│ │ (对话大脑)│ │ 流式TTS │ │ GPU 口型推理  │
└───────┘ └────────┘ └────────┘ └─────────────┘
        横切：延迟打点 ｜ 测试集回归 ｜ 缓存（高频回复复用）
```

核心思想：**各段流水线并行**（TTS 首包输出后即开始口型与播放，不等待完整音频），全链路延迟不是各段串行累加，而是由流水线重叠决定。

### 3.2 模块职责（backend/src/）

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `asr/` | 流式语音识别 | FunASR/Paraformer 流式；分片推进不等待 VAD 端点 |
| `brain/` | 对话大脑 | 统一模型供应商抽象；流式输出（SSE） |
| `tts/` | 流式合成 | 首包优化；**word-level 时间戳输出（音画同步关键）** |
| `lip/` | 口型驱动 | MuseTalk 推理服务化（P1 跨机 HTTP，见 SPEC §2.1）；帧率控制；显存记录 |
| `render/` | 播放链路 | WebRTC 视频流；音画时钟对齐（音频时钟为准） |
| `vad/` | 打断检测 | **P1 无后端实现**（ADR-004）：VAD/端点由前端 AudioWorklet 承担，后端只做「收到音频就识别」；原 `src/vad/` 是空目录，已于 2026-09-15 删除。P2 若评估迁移再建模块 |
| `api/` | 路由与会话 | 状态机（listening/thinking/speaking/interrupted）；SSE 事件 |
| `eval/` | 测试集 + 回归 | 延迟/同步/质量/并发四类脚本，独立于业务代码 |

## 4. 接口定义（MUST）

### 4.1 会话状态机

状态：`listening → thinking → speaking → listening`（循环）；任意时刻收到 VAD 打断 → `interrupted → listening`。

### 4.2 前端 SSE 事件流

| 事件 | 载荷 | 说明 |
|---|---|---|
| `thinking` | 阶段标记 | 进入对话大脑 |
| `brain_token` | 文本增量 | 流式出字（前端实时显示） |
| `tts_audio` | 音频分片 + 时间戳 | 流式语音包，首包即播 |
| `lip_video` | **H.264 整句片段** + `start_ms` | 口型片段，按音频时钟排队播放（ADR-005，**v1.2 默认**） |
| `lip_frame` | 单帧 + `pts_ms` | 逐帧路径，**仅 `transport=frames` 时启用**（A/B 对照用，非默认） |
| `interrupted` | 阶段标记 | 打断已生效（本轮不再发 `done`） |
| `done` / `error` | 结束 / 错误 | 载荷与错误码见 SPEC §2 / §6 |

### 4.3 TTS 接口要求（音画同步前提）

- 必须输出 **word-level 时间戳**（每个词/分片的起止时间），口型帧调度以音频时间戳为时钟基准
- 首包延迟 ≤ 300ms（P2 实测后回填）

### 4.4 配置中心（config.yaml）

| 段 | 关键项 |
|---|---|
| `asr` | 模型名 / 分片粒度（`model`、`chunk_size`）——⚠️ **只有这两项被代码读取** |
| `llm` | 云端模型/本地兜底模型/base_url/key/**人格**（`persona`：`teacher` 教育（默认）/ `cs` 客服，见 `brain/persona.py`，ADR-007） |
| `tts` | 模型名/首包策略/时间戳开关 |
| `lip` | 模型名/分辨率/帧率/批大小 |
| `cache` | 高频回复缓存开关/相似度阈值 |

**纪律（v1.9 教训）**：配置项必须**被代码真实读取**。`asr` 段曾有 6 个字段**全部无人读取**
（`asr/streaming.py` 全硬编码），且 `chunk_size` 的值与实现不符（写 `[5,10,5]`，跑的是 `[0,10,5]`）
——配置中心沦为"文档债务"。**加配置项的同批必须改代码去读它**；改配置前先
`grep -rn "<字段名>" backend/src/` 确认它真的生效。

### 4.5 模块目录

```
backend/
├── src/
│   ├── api/ asr/ brain/ lip/ render/ tts/    （vad/ 已删：VAD 归前端，ADR-004）
│   ├── config.yaml
│   └── ...
├── eval/                   ← 测试集、回归脚本、报告
└── tests/
frontend/                   ← 语音采集 + 视频播放 + 状态展示
data/                       ← 测试音频/视频/评估集
```

## 5. 非功能需求（MUST）

### 5.1 延迟预算（各段目标值，P2 实测后回填）

| 段 | 目标 | 说明 |
|---|---|---|
| ASR 首字 | 单块处理 ≤300ms ✅ **实测 166ms**（CPU RTF 0.27）；首字端到端 **≈766ms** ⚠️ | 流式分片，不等端点；上行往返实测 ~250ms/片。**600ms/块粒度下「首字端到端 ≤300ms」不成立**——原目标仅对单块处理成立（EVAL-P1 v1.2 修正，2026-09-02） |
| LLM 首 token | < 800ms ⚠️ | 流式输出；实测 503~1108ms 波动、均值 ~740ms（2026-09-02 回填） |
| TTS 首包 | < 300ms | 首包即播，流水线并行 |
| 口型首帧 | < 400ms | 预加载 + 帧缓冲 |
| **端到端** | **< 2s** | 用户说完 → **首包开口**（音频首包）；口型首帧单独记录（见上行），两者不同时。流水线并行，非串行累加 ⚠️ 实测修正 |

### 5.2 评估体系（五维）

| 维度 | 指标 | 方法 |
|---|---|---|
| 延迟 | 端到端 / TTFT / 各段分解 | 固定测试集 + 自动打点，同口径回归（量化指标见评估台账） |
| 音画同步 | 时差量化 / 打断响应时间 | 自研测量脚本（音频能量 vs 口型运动时序）+ 人工抽检 |
| 质量 | 口型准确率人工评分（1-5） | 固定测试集 + 标注口径说明 |
| 稳定性 | 连续对话时长 / 掉帧率 / 失败率 | 压测脚本 |
| 并发 | 单卡路数 / 排队延迟 | 并发脚本（云 GPU） |

### 5.3 环境策略

| 环境 | 角色 |
|---|---|
| 本机 | 链路开发、小模型验证、编排/状态机/前端调试、延迟打点框架 |
| 云 GPU（按小时） | 口型推理、FPS/显存记录、批处理/量化实验、并发压测、流式时序验证 |

**P1 跨机协作模式**：本机跑 TTS/ASR/编排/前端，云 GPU 跑 MuseTalk 推理服务（HTTP，接口见 SPEC §2.1）。P1 语义：本机 tts 模块合成完整音频 → 调云 GPU `POST /api/v1/lip/infer` → 返回整段帧序列；P2 演进为流式帧。

### 5.4 已知坑（禁止重新踩）

1. GPU 驱动/CUDA 版本与 PyTorch 匹配（云镜像优先，本地装 CUDA 版 torch）
2. 模型权重下载：国内优先 ModelScope
3. 流式合成时序：不输出完整音频再对口型——先验证时间戳可用性再设计帧调度
4. 音画不同步的定位链路：先查合成时间戳 → 再查口型帧缓冲 → 最后查播放时钟
5. 评估工具校准优先：工具/裁判自身的坑先排除，再归因系统（避免把工具 bug 当成系统短板）

| 问题 | 回答要点 |
|---|---|
| 用的什么模型？你做了什么？ | 开源模型（口型/语音合成/语音识别），自己做全链路编排 + 延迟预算 + 评估 |

| 为什么不自研口型模型？ | 工程岗定位；开源模型成熟，壁垒在链路编排与评估体系 |
