# ADR-004：VAD 打断归属（前端 vs 后端）

> 文件名：`ADR-004-VAD归属.md`
> 类型：adr
> 状态：已接受
> 读者：任何想知道"为什么这么选"的人（含 AI）
> 结论：P1 阶段 VAD 由前端实现（AudioWorklet），通过 HTTP 打断信号通知后端；P2 评估是否迁移至后端

## 背景

打断检测（VAD，语音活动检测）需要监听用户语音。存在两种实现位置：

- **前端实现**：浏览器 AudioWorklet 检测到用户插话 → HTTP POST `/interrupt` 发送打断信号（对应状态机 `SPEAKING → INTERRUPTED`）
- **后端实现**：与 ASR 共享同一音频流，减少上行带宽，但需要同步处理 ASR 与 VAD 的音频源，链路复杂度高

## 决策

我们将采用**分阶段归属**：

- **P1 阶段**：VAD 由前端实现（AudioWorklet），检测到用户插话后通过 HTTP POST `/api/v1/session/{session_id}/interrupt` 发送打断信号。
- **P2 阶段**：评估是否将 VAD 迁至后端（与 ASR 共享音频流，减少上行带宽），若迁移则更新本 ADR（状态改"已取代"，指向新 ADR）。
- DESIGN §3.2 `vad/` 模块：P1 仅预留接口，由前端 VAD 先提供服务。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| P1 即后端 VAD | 需与 ASR 复用同一音频流并保持时序一致，链路复杂度高，拖慢 P1 交付 |
| P1 不做打断 | 打断是核心体验需求（PRD FR-06），不可裁剪 |

## 后果

- 正面：P1 快速落地；前端 AudioWorklet 技术成熟、实现简单
- 负面：上行带宽多一份语音数据（语音分片仍需上行）；前后端各维护一部分打断逻辑，接口契约需严格（见 SPEC §5.2）
- 中性：P2 若迁移，本 ADR 状态改"已取代"并指向新 ADR（编号递增不重用）
