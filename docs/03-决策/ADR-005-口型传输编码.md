# ADR-005：口型帧跨机传输改用 H.264 分段

> 文件名：`ADR-005-口型传输编码.md`
> 类型：adr
> 状态：已接受
> 读者：任何想知道"为什么口型不传逐帧 JPEG 而传视频"的人（含 AI）
> 结论：口型帧的**跨机传输**从逐帧 JPEG base64 改为整句 H.264 片段（base64 mp4），因实测跨机链路仅 ~0.96 MB/s，逐帧 JPEG 16.2s/句不可用，而同帧 H.264 仅 387 KB（41×）

## 背景

ADR-001 定下双环境分工：口型推理在云 GPU，编排与渲染在本机。因此口型帧必须**跨机传输**。SPEC §2.1 的 P1 契约规定响应为 `frames[{frame_b64, pts_ms, frame_idx}]`，`frame_b64` 为 JPEG（v1.1 勘误时已括注"JPEG（P1）/H.264（P2）"）。

2026-09-14 口型服务化落地后实测（证据见 `backend/eval/reports/lip_service_check.md`）：

| 项 | 实测值 |
|---|---|
| 本机↔云链路 | **0.96 ~ 1.02 MB/s**（三种网络对照均落在 0.9~1.0，60MB 全程平坦 → 硬性限速） |
| 云机自身带宽 | 下行 6.6~18 MB/s、上行 3.5~4.0 MB/s（**云侧不是瓶颈**） |
| 逐帧 JPEG 体积 | **15.52 MB / 8s 音频**（200 帧，79.5 KB/帧） |
| 同帧 H.264 CRF26 | **387 KB**（含音轨） |

即：一句 7s 回答用逐帧 JPEG 需传输 **~15 秒**（实测端到端口型首帧 32.4s）；而链路、隧道实现、加密算法、并发路数均已验证无优化空间——**唯一可用的杠杆是减少传输量**。

## 决策

口型帧的**跨机传输载体**改为 **H.264（MP4 容器，`yuv420p`，CRF 26）整句片段**：

1. 云侧 lip 服务在生成并融合完整句帧后，用 ffmpeg（rawvideo 管道输入，不落临时文件）编码为单个 mp4，base64 返回。
2. 新增响应字段 `video_b64` / `duration_ms` / `n_frames`；返回体由"整段帧序列"变为"一个视频片段"，**P1「一句音频一次请求、返回整句素材」的语义不变**（SPEC §2.1 原文），变的是编码载体。
3. SSE 新增 `lip_video` 事件（替换 `lip_frame` 序列）；前端按 `start_ms` 把片段排入音频时钟播放队列。
4. **渲染输出仍为形象原分辨率（704×1216）**，符合 SPEC §4.3「输出分辨率 = 输入形象视频的分辨率」——H.264 只是**传输编码**，不改渲染规格。
5. 保留 `lip.transport` 配置开关（`h264` | `frames`），P1 逐帧路径不删除——**A/B 对照必须可复现**（本项目一贯要求"优化了多少必须能测"）。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| 保持逐帧 JPEG（P1 原样） | 实测传输 16.2s/句、端到端口型首帧 32.4s，交互不可用 |
| 降低 JPEG 质量 / 降分辨率 | JPEG 只做帧内压缩，q80→q50 收益远小于帧间压缩；降分辨率违反 SPEC §4.3「输出=形象分辨率」 |
| 优化隧道（换加密 / 并发 / 换协议） | 实测无效：加密算法无差别（默认 0.71 / aes128-gcm 0.92 / chacha20 0.91 MB/s）、客户端实现无差别、4/8 路并发不放大、60MB 平坦曲线 → 硬性限速 |
| 换网络 | 三网对照均 ~1MB/s（校园 0.97 / 网络A 0.89 / 网络B 1.02），换网无收益 |
| 只传 256×256 人脸 crop，前端合成 | 需前端实现遮罩合成，改动面更大；且**当前瓶颈是传输量而非合成位置**，P2 再评估（届时可复用本 ADR 的度量方法） |
| WebRTC 实时推流（DESIGN §4 的 P2 方向） | P2 方向无疑是终局，但需信令/SDP/ICE 全套，且当前瓶颈（~1MB/s）下 WebRTC 同样受链路限制；先解决载荷，再谈协议 |

## 后果

- **正面**：传输量降 **41×**（15.52 MB → 387 KB），校园网实测单句 0.39s；服务端省去逐帧 base64 编码；前端播放逻辑由"逐帧调度+丢帧"简化为"按句排队播放"
- **负面**：云侧新增 ffmpeg 依赖；引入**编码延迟**（整句编码耗时需在云 GPU 上补测，本 ADR 生效时实例已关机）；前端需处理"片段未到齐时的等待/降级"
- **中性**：SPEC §2.1 的 `frame_b64` 字段与 `lip_frame` 事件保留为兼容路径（配置切换）；V-05 音画同步测量口径不变（仍以音频时钟为基准）
- **风险**：H.264 单片段在"句子很长"时仍会线性增大（7s→387KB，20s→~1MB），若未来回答更长，需演进为**分片流式**（与 SPEC 的 P2 一致）
