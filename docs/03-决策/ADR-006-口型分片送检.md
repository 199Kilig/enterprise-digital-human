# ADR-006：口型按音频分片送推理

> 文件名：`ADR-006-口型分片送检.md`
> 类型：adr
> 状态：已接受
> 读者：想弄清"数字人的嘴为什么比声音慢"的人（含 AI）
> 结论：口型从「整句音频一次送推理」改为「每 ~1s 音频分片送一次」；配合修掉 `localhost` 名字解析的 2 秒开销，首片段偏差从 **+5274ms 降到 +205ms**，后续片段**全部提前到达**（排队即同步）

## 背景

ADR-005 把口型传输从逐帧 JPEG 换成 H.264 后，用户在实际界面（假口型服务回放）报告：
**"声音和视频中的口型延迟很大，大约差两秒左右"**。

量测方法：`eval/verify_lip_sync.py` 以首个 `tts_audio` 分片到达时刻为音频时钟原点，
对每个 `lip_video` 计算 `late_ms = 到达时的音频时钟 − start_ms`（正=晚到，负=提前）。

改造前实测（3 句回答，整句送检 + `service_url` 写 `localhost`）：

| 片段 | 应在(音频时钟) | 实际到达 | 迟到 |
|---|---|---|---|
| 0 | 0ms | 5274ms | **+5274ms** |
| 1 | 7289ms | 7388ms | +99ms |
| 2 | 8898ms | 10189ms | +1291ms |
| 3 | 15147ms | 12479ms | −2668ms |

排查出**两个互相独立的真因**：

**真因 A（占 2 秒）：`localhost` 名字解析开销。** 后端 `lip.service_url` 写作 `http://localhost:8002`。
本机实测（`eval/probe_call_path.py`，同一服务同一台机器）：

| 调用方式 | 3 次耗时 |
|---|---|
| requests + `127.0.0.1` | 5.4 / 5.1 / 22.6 ms |
| urllib + `127.0.0.1` | 3.7 / 4.0 / 2.9 ms |
| requests + `localhost` | **2034 / 2028 / 2049 ms** |
| urllib + `localhost` | **2029 / 2056 / 2050 ms** |

后端逐片日志 `[lip] done … call_ms=2039` 与之一致——**每次调用白付约 2 秒**，
与口型推理、TTS 全无关系。

**真因 B：整句才送推理。** 旧实现在 TTS 把**整句**音频合成完之前不送口型，
即偏差 ≈ 该句音频合成耗时；而音频是"首包即播"（SPEC §3.5 规则 1），于是口型必然落后一整句的合成时间。
实测 TTS 合成速率 **1.95~2.28× 实时**（10.1s 音频用 5.2s 产出）——**这段余量本可让口型提前就绪，却被整句送检浪费了**。

## 决策

1. **后端按音频分片送口型推理**：`tts_consumer` 每累积 `lip.chunk_ms`（默认 1000ms，16k 单声道 PCM16 = 32 字节/ms）
   就切片投递到口型队列，**不等整句合成完**；句尾残片短于 `lip.min_tail_ms`（默认 200ms）不单独推理。
2. **所有本机服务 URL 一律写 `127.0.0.1`，不写 `localhost`**（`config.yaml`、`musetalk_engine.py` 默认值、`/health` 探测）。
3. 片段仍由前端按 `start_ms` 排队播放（SPEC §3.5 2b 不变）——**提前到达是正常的，排队等到点播即同步**。

改造后实测（同一问题、同一假口型服务）：

| 片段 | 迟到 | 片段 | 迟到 |
|---|---|---|---|
| 0 | **+205ms** | 7 | −4379ms |
| 1 | −442ms | 8 | −4989ms |
| 2 | −1071ms | 9 | −5529ms |
| 3 | −1867ms | 10 | −6173ms |
| 4 | −2501ms | 11 | −6697ms |
| 5 | −3186ms | 12 | −7498ms |
| 6 | −3751ms | 13 | 全部提前 |

首片段 +205ms（人眼可辨阈值 500ms 以下），**后续 13/13 片全部提前到达**。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| 保持整句送检，只修 `localhost` | 首片段仍落后一整句合成时间（实测 5.3s 中约 3.3s 来自此项） |
| 音画同步优先：等首片口型就绪再开播音频 | 完美同步，但首声延迟 +N 秒，**直接违反 PRD 端到端 <2s** 的验收口径；且用户要的是"能听见就先响" |
| 固定补偿：统一延迟音频若干毫秒 | 偏差非恒定（受句子长度/TTS 速率影响），固定补偿治不了根 |
| 客户端合成（只传 256×256 crop） | 解决的是**真实 GPU 上融合 30fps 追不上**的问题，与本 ADR 的"派发时机"是两件事，留待后续（ADR-005 已列为待评估） |
| 增大分片（如 2s） | 分片越大，"等这一片"的时间越长，偏差直接变大；分片越小请求数越多。1000ms 是当前折中，**可在 config 调** |

## 后果

- **正面**：首片段偏差 5274ms → 205ms（**改善 96%**）；后续片段全部提前到达，音画同步由"必然落后"变为"排队即对齐"；
  分片粒度可配置，便于后续按真实 GPU 的生成耗时调优
- **负面**：口型推理调用次数从"每句 1 次"变为"每秒 1 次"（本例 14 次）——
  真实云 GPU 上每次调用有固定开销（音频特征 + 25 帧生成 + 编码 + 传输），需实测确认单片耗时 < 1000ms，
  否则队列会积压（**这是开机后必须补测的头号项**）
- **中性**：SPEC §2.1 原文"P1 语义为一句音频一次请求"据此修订为"按音频分片请求"（SPEC v1.3）
- **风险**：分片边界处 MuseTalk 的音频上下文（`audio_padding` ±2 帧 ≈ ±80ms）变短，可能在边界产生轻微口型不连续；
  另前端每秒切换一次 `<video>` 片段，需观察是否有闪烁
