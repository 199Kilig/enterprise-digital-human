# ADR-010：口型链路提速走实现优化，不做架构重写

> 文件名：`ADR-010-口型提速不走架构重写.md`
>
> 类型：adr
> 状态：已接受
> 读者：任何想知道"为什么不用业界最新的帧级流式方案"的人（含 AI）
> 结论：瓶颈在融合实现而非架构；把官方 PIL 融合换成纯 numpy 等价实现即让 rtf 1.065→0.711，
> 不换模型、不换传输协议、不重写编排；帧级自回归与 WebRTC 维持 ADR-005 的 P2 定性。

## 背景

用户报障："嘴型和声音的延迟很大，第一句话都说出去好久了嘴巴才动，且视频流是一段一段送过来的"。

逐跳实测（2026-09-23，详见 `RUNBOOK-环境记录.md` §3.20）：

| 环节 | 实测 | 判断 |
|---|---|---|
| 云 GPU 单片推理 | `total=1065ms`（`gen=290ms` @86fps） | **rtf 1.065 > 1** |
| 分解 | audio 12 + gen 290 + **blend 425** + 编码 ~338 | blend 是最大单项 |
| 本机→云隧道往返 | 1.15~1.33s/片 | 不是瓶颈 |
| TTS 产出 | 4.7s 出 13.8s 音频 | 快（超实时） |
| 后端派发/发送 | dispatch 4s 入队、emit 15.4s 全发 | 正常 |

**rtf > 1 是结构性事实**：口型产出（1065ms/片）慢于音频播放（1000ms/片），队列只会越积越深，
永远追不上。这与 ADR-006 负面栏预警一致——"需实测确认单片耗时 < 1000ms，否则队列会积压
（这是开机后必须补测的头号项）"。

同期收到两份外部 AI 评估报告，均主张**推翻现有架构重做**，建议：帧级自回归生成（对标
DyStream/ARIG）、服务端维持跨帧推理状态（KV Cache 类）、传输层由 HTTP/SSE 改为 WebRTC/WebSocket
双工、把图像后处理搬到 GPU。

## 决策

**提高口型产出速率，走实现层优化；不改变架构选型。**

具体执行（已完成）：在云侧 `deploy/lip_service.py` 中，把官方 `musetalk.utils.blending.get_image_blending`
（PIL 实现）替换为**纯 numpy 等价实现**（新增 `_to_luma` + `blend_frame`，`_blended_iter` 改调）。

**维持不变的既有决议**：
- 继续使用 **MuseTalk**（ADR-003），不换口型模型
- 继续使用 **H.264 整句片段**（ADR-005），不换传输载体
- 继续使用 **~1s 音频分片送检**（ADR-006），不引入逐帧请求
- **SSE 事件流**保持现有形态
- **WebRTC / 客户端合成维持 ADR-005 的 P2 定性**（远期方向，不在 P1 落地）

**效果**（云侧真实对话负载实测）：`total` 1065 → 711~737ms，**rtf 1.065 → 0.72~0.74（<1）**；
融合本身 425 → 116ms（3.6x），且与官方实现**逐像素完全一致**（maxdiff = 0）。

## 被否方案

| 方案 | 否掉原因 |
|---|---|
| **换帧级自回归模型**（DyStream / ARIG 类，一次生成一帧或极小窗口） | ① **模型不兼容**：MuseTalk 权重（8.7G，已部署验证）作废，需重训或更换权重体系，成本与风险远超收益；② **不解决已定位瓶颈**：本链路瓶颈在融合实现（425ms/25帧），不在产出粒度；③ **会加重背压**：帧级推送使 SSE 事件数从 ~11 个增至 ~300 个（12s × 25fps），在队列积压未解时只会更堵；④ **与 ADR-006 决议冲突**：其隐含的"等口型就绪再播"已被 ADR-006 否决（违反 PRD 端到端 <2s 口径） |
| **传输层改 WebRTC / WebSocket 双工** | ADR-005 已定性为 P2 终局；且实测该瓶颈**不在协议层**——ADR-005 的三种网络对照（0.89~1.02 MB/s）、加密算法对照（0.71/0.92/0.91 MB/s）、4/8 路并发均无显著差异，硬性限速在链路层而非协议层。另注：LiveTalking 的公开配置是 `--transport webrtc --model musetalk`，即"MuseTalk + WebRTC"可行，但那是换**传输**不是换**模型**，且仍需信令/SDP/ICE 全套 → 留在 P2 |
| **服务端维持跨帧推理状态**（Rolling KV Cache / Persistent State） | MuseTalk 是两阶段非自回归模型（UNet + VAE 逐帧解码），**没有可保留的跨帧自回归状态**；该建议实质上等价于"换模型"，否掉原因同上 |
| **图像后处理搬到 GPU** | 已实测无收益（1.0x）：每帧要过 PCIe 的数据量（`ori` 2.57MB + `face` 0.17MB + `mask` 0.39MB 上行、`out` 2.57MB 下行 ≈ **5.7MB/帧**）远大于真实计算量（362×362×3 的乘加），**瓶颈是传输与张量分配而非算力**；且融合结果最终必须回 CPU 交给 ffmpeg（NVENC 不可用，见下），D2H 无法避免。实测 PIL 413ms / torch GPU 394ms / **numpy 116ms** |
| **编码器切 NVENC（把 H.264 编码移到硬件编码器）** | 云上 `ffmpeg 4.2.7`（2019）的 NVENC SDK 不认 RTX 4090（Ada，2022）：`OpenEncodeSessionEx failed: unsupported device (2)` / `No NVENC capable devices found`。要可用须升级 ffmpeg，会危及当前已跑通的镜像环境（ADR-001 的镜像约束），**代价大于收益** |
| **把融合放线程与 GPU 推理重叠** | 2026-09-14 已实测：线程争用使 GPU 侧 51.4fps → 23.5fps，端到端 7.8s → 9.4s，**反而更慢**（见 `lip_service.py::_recon_frames` 内注释） |

## 后果

**正面**
- **rtf < 1 达成**，口型产出快于音频播放，队列不再积压（ADR-006 的"头号补测项"结清）
- **连带修好"~80 秒缺口"**：该现象在 rtf > 1 时表现为"后端已发出、前端 95s 才收到"，
  经逐层排除（后端发送 / 网络 / Vite 代理 / 前端代码均清白）确认其真因是**上游队列背压**，
  rtf 改善后自行消失，**未改任何前端代码**
- **零新增依赖、零协议变更**：纯 Python 实现替换，不引入新库、不改接口契约、不动前端
- 推理链路更快后，后续调小 `chunk_ms`（ADR-006 预留的调优空间）成为可能

**负面 / 需承担**
- 融合实现从"引用官方库函数"变为"**自行维护的等价实现**"→ **云侧升级 MuseTalk 时必须复核
  等价性**（用 `URL.createObjectURL` 级别的逐像素比对，或重跑本次的 E4 对照脚本）；
  官方若修改 blending 语义，本项目不会自动跟随
- 该实现依赖 `mask` 为 3 通道这一观测事实（云端 mask PNG 以 RGB 存盘，三通道取值相同）；
  若 avatar 预处理产物改为单通道灰度，`_to_luma` 需相应适配（已做分支处理，但需留意）

**中性**
- 帧级自回归与 WebRTC 仍是业界演进方向，**维持 ADR-005 的 P2 定性**：待 P1 指标达标且
  确有更高实时性需求时再评估
- 本次未处理"音画偏差"（口型与语音的绝对对齐）：`useLipVideo` 的策略是"片段到达即从头播、
  不假装同步"，属已知表现，是否处理另行决策
