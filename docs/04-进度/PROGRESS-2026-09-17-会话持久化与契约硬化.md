### 二、外部审查清单的核实与选择性硬化（4+1 条）

对 20 条清单**逐条核对代码**后，只落地与项目差异化方向（延迟/音画/并发）相关的项：

- [x] **#6 口型队列背压**（音画同步风险，且与 RUNBOOK §3.14 待验项吻合）：`lip_in_q` 限长（`config.yaml lip.queue_max`，默认 8）+ **满则丢最旧**；`done` 事件新增 `lip_dropped` 暴露丢帧数。理由：TTS 合成快于单 GPU 串行推理，无界队列会让片段落后音频时钟 → **丢帧好过整体延迟**
- [x] **#10 TTS 连接独占**：`CosyVoiceTts.stream` 加独占锁 + 按 `task_id` 过滤 JSON 事件。真因：DashScope 的**音频帧是裸二进制、不带 task_id**，接收侧无法区分 task → 并发用同一连接会串音频（当前 `tts_consumer` 串行，属防御性；一旦有人改并发就立刻出错）
- [x] **#2 常量收口**：新增 `src/constants.py`（`SAMPLE_RATE` / `BYTES_PER_MS` / `ms_to_bytes` / `bytes_to_ms`），收敛原先散落三处的 `32 字节/毫秒`（`routes.py` `*32`、`lip/engine.py` `32000.0`、`tts/cosyvoice.py` `BYTES_PER_MS`）。理由：CosyVoice2 原生 24kHz 时三处会同时错
- [x] **#11 任务收尾**：`chat_stream` 的 `finally` 从"只 cancel"改为 **cancel + `await gather(return_exceptions=True)`**，避免 CancelledError 无人接管与子任务收尾被跳过
- [x] **#20 契约标注**：SPEC §2 标注 `buffer_audio/buffer_lip` **P1 未落地**（实际队列是 `chat_stream` 局部变量）；`AsrChunk.confidence` 已在 v1.4 标注恒为 0

## 追加（同日）：ASR 交互缺陷修复 + 真人准确率能力

用户实测反馈「点击说话结束后没有发送字」「ASR 感受不好」后逐条核实：

### 修：手动点"结束"不发字（必现缺陷）

- 根因：`useMicCapture` 暴露的 `stop` 传 `sendEndpoint=false` → `onEndpoint` 永不触发 → 文本只留在 `liveText`
- 而按钮 tooltip 承诺的正是「点击结束**并发送**」（`ConversationPanel`）→ **实现没跟上 UI 文案**
- "再点说话又看到上次的字" = 三重叠加：`stop` 不清 `liveText` + `recording=false` 时气泡整体隐藏
  + 再开会话时同一气泡把残留文本又渲染出来（**不是**"文字被保存后又显示"）
- 修：`stop` 改传 `true`（手动结束 = 端点）；toggle 两侧都清 `liveText`

### 新增：真人麦克风准确率能力

- 后端 `ASR_DEBUG=1` → 每次语音会话的**完整音频 + 识别文本**落盘 `eval/reports/asr_capture/`
- `eval/verify_asr_mic_accuracy.py`：按采集时间顺序与测试集条目对齐 → 字准率 + 最差条目
- `eval/verify_asr_models.py`：**流式 vs 离线模型精度对比**（two-pass 是否值得做的判据）
- 实测：落盘 wav **36864 帧 / 2.30s / 16kHz 单声道**，字节数与源音频一致；识别 `你们家运费怎么算` 全对

### 契约缺口（排查时暴露，已补 SPEC v1.9）

- `POST /api/v1/asr/chunk` **此前只有数据契约（`AsrChunk`）、没有 HTTP 端点文档**，而前端一直在用 → 补 §5.4
- `seq == 0` 语义（**重建识别器**）此前只存在于代码；破坏递增会让识别**退化为只认最后 600ms**
  （实测复现：恒发 `seq=0` → 识别出「嗯」）→ 已写进 SPEC 并标注后果
- `config.yaml` 的 `asr` 段：**6 个字段代码一个都不读**，且 `chunk_size` 值与实现不符
  （config `[5,10,5]` vs 代码 `[0,10,5]`）→ **已收口（同日）**：`model` / `chunk_size` 接回代码
  （实测改 config 真影响 `CHUNK_STRIDE` 9600→19200）、删除 `provider` / `vad_model` / `streaming` /
  `chunk_stride` 四个名义项；纪律写入 DESIGN §4.4 与 RUNBOOK §3.16

### 修：两个"真机才暴露"的缺陷（用户用 `start.bat` 实测反馈）

**① "ASR 识别只能用一次" —— 异步 start 撞只读守卫（前端竞态）**

- 症状：第一次识别正常，之后点麦克风**毫无反应**（连报错都没有）
- 根因链：`startMic('barge')`（播报期间开打断监听）是异步的 → 播报很快结束时 effect 重跑，
  此刻 `monitoring` 还是 `false`（`setMonitoring(true)` 未执行到）→ `else if (monitoring)` 不成立 →
  **没人释放这次监听** → 异步 start 落地后 `modeRef.current = 'barge'` → 此后 `start()` 开头的
  `if (modeRef.current !== null) return` 挡掉每一次点击 → 永久失灵
- 修法：① `release()` 递增 `epochRef`，`start()` 完成后核对 epoch（不一致则关掉刚拿到的资源）；
  ② `start()` 遇不同模式改**抢占**而非静默 return；③ effect 里 start 完成后**再核对期望值**
- **后端侧已排除**：同一 session 连跑 3 轮——识别正确 + SSE 完整（thinking→brain_token→tts_audio→done，0 error）

**② "初次说话毫无反应" —— ASR 冷启动 22s**

- 症状：刚用 `start.bat` 启动后第一次说话长时间无反应，试几次才正常
- 根因：`get_model()` 冷启动阻塞 22s，前端每 600ms 一片且 `await postChunk` → 分片全堵在加载上；
  而 `ASR_TIMEOUT` 只统计 `_generate` 内部（不含加载）→ **连超时都不报**，纯粹卡住
- 修法：`routes.py` 加 `lifespan`，启动即**后台线程**预热（不阻塞 uvicorn；失败不影响服务）
- 实测：预热 **23.5s** 完成；**预热后首片 227ms**（未预热 ~22000ms）；这是 RUNBOOK 坑 8 的根治
  （以前靠人手工跑 `prewarm_asr.py`，现在服务自己预热）

> **教训（已写入 RUNBOOK §3.17）**：只读守卫 + 异步获取资源 = 必然出现"幽灵状态"；
> 凡"先检查再异步"处，都要用代际号让在途操作可作废。这类缺陷**离线脚本测不出来**
> （后端连跑 3 轮全正常），只有真机点几下才暴露。
