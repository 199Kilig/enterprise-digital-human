# docs 文档撰写手册（docs-guide）

> 制度依据：一文档一类型 + 双读者投影 + 内容与状态一致 + 价值门槛。写任何 docs 文档前先过本手册。
> 本文件是项目文档体系的唯一宪法：AGENTS.md 的文档规范节、README 地图、各文档模板均指向本文件，不另写副本。

## 0. 写前三问（价值门槛，任一不满足 → 不写 / 并入 / 归档）

| 问题 | 不满足时的动作 |
|---|---|
| 有明确读者和决策场景吗？ | 没人看的不写 |
| 有现成文档能承载吗？ | 能并入就不新建（指标 → 评估台账；决策 → ADR；暂缓 → 暂缓清单） |
| 信息需长期有效吗？ | 一次性过程 → 不落 docs，进 git 提交说明 |

## 1. 文档类型闭集（一文档一类型，目录即类型）

| 类型 | 目录 | 文件名格式 | 定位（只承载这一类内容） | 状态模型 |
|---|---|---|---|---|
| 需求 | 01-需求/ | `PRD-<语义短语>.md` | 做什么、为什么做（禁止写实现细节） | 演进 |
| 方案 | 02-方案/ | `DESIGN-<语义短语>.md` | 怎么做（禁止写"为什么不选别的"） | 演进 |
| 决策 | 03-决策/ | `ADR-NNN-<语义短语>.md` | 为什么这么选（背景/决策/被否方案/后果） | 只增不改 |
| 进度 | 04-进度/ | `PROGRESS-日期-<语义短语>.md` | 本阶段发生了什么变化（**只记增量事件，禁止全量快照**） | 每阶段一份 |
| 复盘 | 05-复盘/ | `RETRO-<语义短语>.md` | 学到了什么（诊断→结论，禁止流水账） | 每阶段一份 |

**命名规则（语义短语）**：用中文短语概括文档内容，≤5 个词，是标题的缩写，不是编号。`PRD-打卡功能.md`、`ADR-004-文档用中文命名.md`、`PROGRESS-2026-08-30-完成文档体系落地.md` 都是合法名；`PRD-123.md`、`PROGRESS-2026-08-30-123.md` 不合法（语义段禁止纯数字/纯日期）。文件名解决"找到"，正文解决"读懂"——语义短语 + 文档地图（见 §5）是检索双保险。

扩展类（按需启用，加进本表不破坏核心五类）：评估台账 `eval-history`、运维手册 `runbook`、测试报告 `test-report`、数据集 `dataset-`、暂缓决策 `pending-decisions`、**知识笔记 `tech`**。

### 扩展类：知识笔记（tech）——服务"未来的我"

| 项 | 值 |
|---|---|
| 目录 | `06-知识/` |
| 文件名 | `TECH-<技术>-<语义>.md`，如 `TECH-SQLAlchemy-动态筛选器.md` |
| 定位 | 我掌握了什么、怎么操作、怎么讲（复盘回忆 + 面试快查）；读者是未来的自己 |
| 模板 | `docs/_templates/TECH-template.md`（六段：触发场景/技术要点/操作步骤/难点与解决/亮点与代码锚点/关联文档） |
| 台账 | 每份笔记必须在 `docs/06-知识/README.md` tech-index 登记一行（强制，未登记 = 校验 FAIL） |
| 何时写 | 阶段结束蒸馏时，用判别问题把关："本轮有没有用到此前不了解的技术/模式？"有才写，避免泛滥 |

知识笔记只记提炼后的成果，不记过程快照（快照进 `docs/_inbox/`）；与项目五类互补——项目文档回答"项目发生了什么"，知识笔记回答"我学会了什么"。

## 2. 双读者投影（内容与呈现分离，禁止维护两份内容）

同一份源，两个视图：

- **人读**：完整叙事版（背景、解释、排版）——HUMAN 区块
- **AI 读**：AGENTS.md 指针 + 文档内 MUST 区块——高熵事实，零叙事

文档内标记约定：

```markdown
## 验收标准（MUST）    ← 事实：AI 必须提取，逐条满足
## 背景与叙事（HUMAN） ← 叙事：AI 投喂时忽略
```

投喂纪律（给 agent 喂文档时的固定指令）：
> "只提取元信息头块 + MUST 区块，忽略 HUMAN 区块。"
> 或先让 AI 做 20 行投影转写（目标/范围/验收标准/约束/关联文档），后续工作以转写为准。

## 3. 元信息头块（定位先行，5 行内说清"这是什么、什么状态、结论"）

```markdown
> 类型：<五类之一>
> 状态：计划中｜执行中｜已完成｜已暂缓｜已废弃
> 读者：<谁会读它，解决他什么决策>
> 结论：<一句话>
```

## 4. 内容与状态一致（防过时图纸）

- **已暂缓/已废弃**：不保留完整设计细节，只留"决策链（假设→证据→结论）+ 归档指针"，一句话注明"完整设计见 git 历史 `<提交或文件@时间>`"
- **执行中**：只写当前阶段内容；完成一段更新一段，不留"将来要做的完整设计"占位
- **量化指标唯一入口**：RAGAS 等指标只进评估台账，其他文档引用时写"见评估台账对应行"

## 5. 产物管道（inbox → 蒸馏 → 类型文档 → 地图登记）

过程与成果分流，docs 只放蒸馏后的成果：

1. **inbox 暂存**：agent 产生的临时产物（当前时刻进度快照、草稿、中间输出、未整理的素材）一律落 `docs/_inbox/`。该目录不进 git、不参与校验、不写进正式文档。
2. **蒸馏**：阶段结束时，用 `docs/_templates/prompts/distill.md` 把 inbox 素材提炼成对应类型的正式文档（先投影草稿 → 按模板成文 → 校验 PASS）。
3. **清空**：提炼完毕的素材删除或移入 `docs/_generated/`，inbox 保持空。inbox 长期不空 = 有素材没蒸馏 = 欠债。
4. **登记**：新文档写完，在 `docs/README.md` 文档地图加一行（文档名/类型/状态/定位）。这是强制项——`validate_docs.py` 发现正式文档未登记 = FAIL。

判断素材归属：能写进哪一类就进哪一类（决策 → ADR，事件 → PROGRESS，教训 → RETRO）；塞不进去的一次性过程内容直接删除，它已经留在 git 提交历史里了。

## 6. 反例自查（本制度的由头）

曾出现"四合一"文档（设计蓝图 + 审计报告 + 执行报告 + 暂停声明）→ 定位不明、内容与状态矛盾、读者不知道它是什么。**新文档不允许出现任何形式的"多合一"。**
